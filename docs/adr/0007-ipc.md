# 0007. A per-user named pipe, checked from both ends

- Status: accepted
- Date: 2026-10-11

## Context

`mosaikctl` (and a second `mosaik.exe` launched while one runs) must talk to the running engine.
The channel must be local, private to the user, safe against a program that takes the name
first, and must never hang either side.

## Decision

- One JSON object per line over `\\.\pipe\Mosaik-<session>-<user SID>`, with a protocol version
  in every message; a request from a newer client gets a plain "update" error.
- The server's pipe is owned by the user, grants access to the user and SYSTEM only, carries the
  server's integrity level as a no-read-up, no-write-up label, refuses remote clients and claims
  the name as the first instance. Each client gets its own instance; every read and write has a
  deadline (idle 30 s, write 5 s); a client that breaks the protocol is told and dropped.
- A client opens the pipe for identification only (the server can never act as the client) and,
  before sending anything, checks that the pipe is owned by the user, labelled medium integrity
  or above, served from the same session, by the expected program (`mosaik.exe` next to
  `mosaikctl`, by path).
- The UI inside `mosaik.exe` uses the same commands in process.

## Evidence

10 named-pipe tests pass on Windows (2026-10-11): round trip; second server told who holds the
name; wrong program refused; nobody listening; a client that leaves before its reply; a stalled
client neither blocks others nor stays connected; malformed, v0 and v2 requests; an oversized
message; stopping; a low-integrity squatter refused. An adversarial review found seven defects in
the first version (listed in the commit), all fixed with tests.

## Consequences

- Talking to an elevated Mosaïk needs an elevated `mosaikctl`; the error says so.
